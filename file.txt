# MASTER PROJECT SPECIFICATION: AI-POWERED CONVERSATIONAL FINANCIAL PLATFORM

## 1. ROLE AND EXPECTATIONS

Act as a principal fintech software architect, senior backend engineer, financial systems engineer, application security engineer and experienced frontend engineer.

Your responsibility is to design and implement a robust, secure, extensible, AI-powered conversational financial platform.

This is not a conventional banking application with a chatbot attached.

It is a conversational financial assistant through which customers interact with financial services using natural language and voice messages, primarily through WhatsApp.

The system must be engineered with banking-grade architectural principles, strong transaction integrity, strict security boundaries, traceability, fault tolerance and reliable financial recordkeeping.

Do not build a superficial prototype that only looks functional.

Do not implement fake financial operations and present them as genuine transactions.

During development, use sandbox financial providers and clearly identify simulated transactions.

Production financial operations must remain disabled until the appropriate licensed financial partner, regulatory approvals, security reviews and operational controls are established.

# 2. PRODUCT VISION

Build a conversational financial platform that allows customers to interact with financial services naturally.

A customer should be able to send a WhatsApp message such as:

- Send ₦2,000 to Mum.
- Transfer ₦5,000 to John.
- How much money do I have?
- Show my last five transactions.
- Buy ₦1,000 airtime.
- Buy 2GB data.
- What did I spend yesterday?
- Send airtime to this phone number.
- Did my last transfer go through?
- Send ₦3,000 to my saved electricity payment recipient.

The assistant should understand the request, identify the required information, validate the request, obtain secure authorization and communicate with the appropriate financial service.

The experience should feel like having a personal financial assistant rather than interacting with a traditional banking interface.

# 4. ARCHITECTURAL PRINCIPLES

Use a modular monolith initially, with clearly defined domain boundaries.

Do not introduce microservices merely for architectural appearance.

The system must be designed so that individual modules can eventually be extracted into independent services without rewriting the entire application.

Apply:

- Domain-driven design principles.
- Separation of concerns.
- Dependency inversion.
- Explicit service boundaries.
- Repository patterns where appropriate.
- Application services.
- Domain services.
- Strict DTO validation.
- Strong typing.
- Explicit transaction boundaries.
- Centralized exception handling.
- Immutable financial records.
- Explicit state machines for financial operations.

Business logic must not live inside controllers.

Controllers should handle HTTP concerns and delegate business operations to application services.

Financial rules must not be implemented inside AI handlers.

AI must never directly modify financial balances or execute financial operations.

## 5.6 Transaction management module

This is one of the most important modules.

Treat transaction processing as a critical financial subsystem.

Every financial operation must have:

- Unique internal transaction ID.
- Unique idempotency key.
- Customer reference.
- Transaction type.
- Amount.
- Currency.
- Fee information.
- Provider reference.
- Destination reference where applicable.
- Current transaction state.
- Creation timestamp.
- Last update timestamp.
- Relevant audit information.

Supported transaction types should include:

- TRANSFER
- DEPOSIT
- WITHDRAWAL
- AIRTIME_PURCHASE
- DATA_PURCHASE
- PAYMENT
- REFUND
- REVERSAL
- FEE
- ADJUSTMENT

Implement an explicit transaction state machine.

Suggested states:

- CREATED
- VALIDATING
- AWAITING_AUTHORIZATION
- AUTHORIZED
- PROCESSING
- SUCCESSFUL
- FAILED
- PENDING
- REQUIRES_RECONCILIATION
- REVERSED
- CANCELLED

Define valid transitions centrally.

Do not allow arbitrary state updates.

A transaction marked SUCCESSFUL must never be changed to FAILED merely because a later network request timed out.

An uncertain provider response must be treated as an uncertain transaction, not an automatic failure.

Use provider status enquiries and reconciliation to resolve uncertain outcomes.

### Transaction lifecycle

A transfer should follow this general lifecycle:

1. Receive the customer's request.
2. Parse the request into structured data.
3. Validate the amount and currency.
4. Resolve the recipient.
5. Verify the destination details.
6. Check applicable account and transaction limits.
7. Calculate applicable fees.
8. Generate a transaction preview.
9. Request secure customer authorization.
10. Validate the authorization.
11. Create the transaction record.
12. Apply appropriate internal transaction controls.
13. Submit the instruction to the financial provider.
14. Record the provider response.
15. Process verified provider webhooks.
16. Confirm the final outcome.
17. Update the accounting ledger according to the financial event.
18. Notify the customer.
19. Make the transaction available in transaction history.

The exact order of internal reservations, ledger posting and provider submission must be designed around the partner's settlement and custody model.

Do not assume that every transfer can be treated as an instantaneous operation.

### Idempotency

Implement idempotency for all financial operations.

If the same request is submitted multiple times, the system must not execute duplicate transfers.

Idempotency must cover:

- Customer-initiated requests.
- Provider API submissions.
- Webhook processing.
- Background job retries.
- Administrative retry actions.

Use database-enforced uniqueness constraints.

Do not depend on an in-memory cache as the only protection against duplicate transactions.

### Concurrency protection

Protect against simultaneous requests that could cause incorrect balances or duplicate operations.

Use appropriate database transactions, locking strategies and isolation levels.

Define and test invariants for:

- Account balances.
- Available balances.
- Reserved funds.
- Transaction uniqueness.
- Ledger consistency.
- Concurrent withdrawals.
- Concurrent transfers.
- Duplicate provider callbacks.

Never rely on a simple application-level balance check without protecting against concurrent modifications.

# 6. DOUBLE-ENTRY ACCOUNTING LEDGER

Implement a proper double-entry ledger.

Do not use a mutable balance field as the sole source of financial truth.

The ledger must provide an auditable record of financial movements.

Each posted financial event must create balanced debit and credit entries.

For every journal:

TOTAL DEBITS = TOTAL CREDITS

Use an appropriate integer representation of currency in minor units, or a rigorously defined decimal strategy.

For Nigerian naira, document the currency precision and conversion rules.

Never use JavaScript floating-point arithmetic for financial calculations.

The ledger must support:

- Chart of accounts.
- Customer-related accounts where appropriate to the licensed model.
- Settlement accounts.
- Provider clearing accounts.
- Fee revenue accounts.
- Expense accounts.
- Suspense accounts.
- Reversal journals.
- Adjustments.
- Journal references.
- Immutable posted entries.

A posted journal must never be edited or deleted.

Corrections must use compensating entries and explicit reversal references.

Implement ledger posting within appropriate database transaction boundaries.

Ensure that the accounting model correctly represents the licensed partner's actual custody, settlement and safeguarding arrangement. Do not invent customer deposits or platform liabilities that do not exist in the real financial arrangement.

## Ledger invariants

1. Every posted journal balances.
2. Posted entries are immutable.
3. Every journal has a unique reference.
4. Reversals reference the original journal.
5. Duplicate events cannot create duplicate postings.
6. Ledger totals can be independently reconciled.
7. No transaction may silently change historical financial records.

- WhatsApp test or approved staging configuration.

# 26. IMPLEMENTATION RULES

These rules are mandatory.

### Rule 1: Inspect before coding

Inspect the existing repository before making changes.

Identify:

- Existing architecture.
- Existing dependencies.
- Existing modules.
- Existing database schema.
- Existing coding conventions.
- Existing functionality.

Do not destroy working functionality unnecessarily.

### Rule 2: Design before implementation

First establish:

- System architecture.
- Domain boundaries.
- Database relationships.
- Financial invariants.
- Transaction state machines.
- API contracts.
- Security boundaries.
- Integration contracts.

### Rule 3: Never implement financial shortcuts

Do not:

- Store balances as the only financial record.
- Use floating-point arithmetic for money.
- Allow direct balance editing.
- Trust AI-generated transaction instructions without validation.
- Execute a payout without authorization.
- Assume timeouts mean failure.
- Ignore duplicate webhooks.
- Allow arbitrary transaction state changes.
- Retry payouts without checking their original status.
- Use mutable ledger history.

### Rule 4: Complete code, not disconnected snippets

Implement complete, connected functionality.

Do not provide isolated code fragments that cannot work within the project.

For every feature, implement the required database changes, validation, service logic, API contracts, error handling and tests.

### Rule 5: Explain important architectural decisions

Document why a particular financial design was selected.

Do not choose a complicated architecture without a clear reason.

### Rule 6: Verify implementation

Run the relevant tests and static checks.

Do not claim a feature is complete if it has not been implemented and verified.

### Rule 7: Do not invent provider capabilities

Read actual provider documentation before implementing an integration.

If a provider does not support a required operation, report the limitation.

Do not fabricate endpoints, authentication mechanisms, webhook formats or API responses.

### Rule 8: Preserve financial integrity

All financial changes must be traceable.

Every financial operation must have a clearly defined authorization, execution, recording, verification and recovery process.

### Rule 9: Avoid premature microservices

Begin with a modular monolith.

Keep modules sufficiently independent for future extraction.

### Rule 10: Security takes priority over convenience

Never bypass a security control merely to make a demo easier.

Use clearly isolated sandbox implementations when real infrastructure is unavailable.

# 28. FINAL QUALITY STANDARD

The finished system must demonstrate:

- Reliable financial transaction handling.
- Double-entry accounting.
- Strong idempotency.
- Concurrency safety.
- Secure authentication and authorization.
- Immutable accounting records.
- Reliable webhook processing.
- Financial reconciliation.
- Provider abstraction.
- Traceable transaction lifecycles.
- Recoverable background processing.
- Comprehensive automated testing.
- Secure administrator operations.
- Reliable WhatsApp integration.
- Validated AI instructions.
- Clear separation between sandbox and production.

The objective is to build a serious financial technology foundation, not merely an AI chatbot that calls payment APIs.

Prioritize correctness, security, auditability and financial integrity over development speed.

A system must not be described as banking-grade or production-ready merely because these components exist. Its security and financial controls must be independently reviewed, tested and validated before real customer funds are handled.
